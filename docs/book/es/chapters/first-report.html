5  Un primer informe, a mano

Palabras clave

Quarto, publicación reproducible, agentes de programación, Markdown, Python, EPUB, análisis de datos, k-means

En algún lugar del informe de este capítulo hay un número equivocado. El informe se renderiza sin un solo error, se lee perfectamente bien y cita su fuente, y una de sus cifras está desviada en 360,000 visitas. Encontrarla no requiere programar, solo un hábito: poner cada número al lado de los datos de los que salió.

Ese hábito es el Revisa del título de este libro, y este capítulo es donde lo practicas con tus propias manos. Escribes tú cada comando, en la terminal, sobre un informe real: lo copias, lo renderizas, lo revisas, lo registras con Git, lo cambias y deshaces el cambio, lo rompes de tres maneras a propósito y lees los errores. Solo al final el agente hace una edición, y tú revisas su trabajo con los mismos comandos que acabas de aprender. Calcula unos 45 minutos; menos si la terminal ya te resulta familiar.

En este capítulo
  • Copiar un proyecto, entrar en él y renderizarlo desde la terminal.
  • Revisar cada número de un informe contra sus datos, y rastrear uno equivocado hasta donde se escribió a mano.
  • Registrar, comparar y deshacer cambios con git status, git diff, git restore y git commit.
  • Leer un error desde su primera línea, y revisar el cambio de un agente antes de hacer commit.

Partes deel final del Capítulo 4: las herramientas instaladas y ~/quarto-workshop clonado en el paso 5.

Construyes~/first-report, un informe de una página en el que cada número coincide con sus datos, con un historial de Git de dos commits.

Punto de controlno hace falta ninguno: el punto de partida es el punto de control. Si te pierdes, cambia el nombre de tu copia con mv (move, mover, que también cambia nombres), mv ~/first-report ~/first-report-old, y vuelve a copiar el punto de partida (Sección 5.1).

5.1 Consigue los archivos

El paso 5 del Capítulo 4 clonó los archivos del taller en ~/quarto-workshop. Entre ellos hay un informe pequeño, starters/first-report. Cópialo afuera, para que el original quede como estaba. Escríbelo con ayuda de completar con Tab, que ahorra tipeo y atrapa errores: escribe cp -R ~/quarto-workshop/st y presiona Tab, y la terminal termina el nombre, starters/. Cuando encajan varios nombres, presiona Tab otra vez para verlos. Cuando Tab no hace nada en absoluto, ahí no existe ningún nombre que empiece así, y conviene saberlo antes de presionar Enter. En la terminal, en cualquier carpeta:

cp -R ~/quarto-workshop/starters/first-report ~/first-report

cp copia, y -R (recursive, recursivo) copia una carpeta con todo lo que tiene adentro. No imprime nada. Muchos comandos funcionan así: cp, cd y, más adelante, git add no dicen nada cuando funcionan, y solo hablan cuando algo sale mal. En la terminal, el silencio es éxito.

AdvertenciaError frecuente

Si cp dice No such file or directory, tu copia del taller es más vieja que este capítulo: cd ~/quarto-workshop, luego git pull, y luego ejecuta otra vez la línea de cp.

Ahora entra en la copia y mira alrededor. En la terminal:

cd ~/first-report
pwd
ls

pwd imprime la carpeta en la que estás, que termina en first-report (/home/ana/first-report en Linux, /Users/ana/first-report en una Mac, con tu propio nombre). ls enumera seis nombres, en un orden que depende de tu sistema:

ImportantePruébalo

Si todavía no lo hiciste, copia el punto de partida y entra en él con cd ~/first-report.

Terminaste cuando pwd imprime una ruta que termina en first-report, y ls enumera report.qmd y data.

Un nombre con un espacio

La terminal parte lo que escribes en cada espacio, así que el nombre de una carpeta con un espacio necesita cuidado. Pruébalo una vez, desde tu carpeta personal. En la terminal:

cd ~
mkdir "my reports"
cd my reports

cd se queja, con palabras que dependen de tu shell:

bash: cd: too many arguments            (Ubuntu)
cd: string not in pwd: my               (Mac)

cd recibió dos nombres, my y reports. Mantén el nombre de una pieza con comillas, cd "my reports", o con una barra invertida antes del espacio, cd my\ reports. Completar con Tab escribe la barra invertida por ti: escribe cd my y presiona Tab. Luego ordena y vuelve:

cd ~
rmdir "my reports"
cd ~/first-report

Las carpetas de este libro no tienen espacios en el nombre, y las tuyas tampoco necesitan tenerlos: un guion, como en first-report, hace el mismo trabajo.

5.2 Renderízalo tú

En la terminal, en ~/first-report:

uv run quarto render report.qmd

uv run ejecuta un comando en el propio entorno de Python del proyecto (Sección 1.4; la Sección 6.10 tiene más). La primera vez, construye ese entorno a partir de uv.lock, lo que tarda desde unos segundos hasta un minuto, y puede imprimir antes algunas líneas Downloading. Luego Quarto renderiza, e imprime bastante (recortado aquí donde se marca …):

Using CPython 3.12.13
Creating virtual environment at: .venv
Installed 39 packages in 301ms

Starting python3 kernel...[IPKernelApp] WARNING | …
Done

Executing 'report.quarto_ipynb'
  Cell 1/1: ''...Done

pandoc
  to: html
  output-file: report.html
  …
Output created: report.html

Cuando un renderizado funciona, su última línea es Output created: report.html. Las líneas después de pandoc son su configuración, y la advertencia de IPKernelApp es inofensiva (Sección 4.7). Tu versión de Python, la cantidad de paquetes y los tiempos pueden ser distintos.

Abre la página. En la terminal, ejecuta open report.html (Mac), xdg-open report.html (Linux), o explorer.exe . y luego haz doble clic en report.html (Windows, en Ubuntu). El navegador muestra:

Five London Sights

Five of London’s best-known sights had 25,036,711 visits between them in 2025. The most visited was the Natural History Museum (South Kensington), with 7,116,929, and 4 of the five are free to enter.

Tate Modern, on the South Bank, had 4,154,266 visits.

Source: ALVA, “Visits made in 2025 to visitor attractions in membership with ALVA” (only ALVA member attractions are counted).

(Es decir: cinco de las atracciones más conocidas de Londres sumaron ese total de visitas en 2025; la más visitada fue esa, con esas visitas, y esa cantidad de las cinco tiene entrada gratuita. Tate Modern, en la orilla sur del Támesis, tuvo esas visitas. La fuente es la tabla de visitas de 2025 de ALVA, que cuenta solo las atracciones miembro de ALVA.)

Ahora abre la carpeta misma: open . (Mac), xdg-open . (Linux) o explorer.exe . (Windows, en Ubuntu), donde . significa “esta carpeta”. El explorador de archivos muestra los mismos archivos que ls, más los nuevos que hizo el renderizado: report.html y report_files/. La terminal y el explorador de archivos son dos vistas de una misma carpeta.

ImportantePruébalo

Renderiza el informe y abre report.html.

Terminaste cuando el renderizado termina con Output created: report.html, y la página muestra el total de las cinco atracciones.

5.3 Revisa cada número contra los datos

El renderizado funcionó. Eso demuestra que el código se ejecutó, no que el informe esté bien. Mira los datos. En la terminal, en ~/first-report:

cat data/visits.csv

cat imprime un archivo. Un CSV es una tabla en texto plano, con comas entre las columnas. Este tiene una primera línea que nombra sus siete columnas, y luego cinco filas, una por atracción. Cada fila lleva su source, su url y su fecha retrieved, así que las líneas son largas y se ajustan. Pide solo las dos primeras columnas:

cut -d, -f1,2 data/visits.csv

cut conserva algunas columnas de cada línea: -d, dice que las columnas están separadas por comas, y -f1,2 conserva la primera y la segunda. Corta en cada coma, incluso en una que esté entre comillas, así que aquí es seguro solo porque las dos primeras columnas no tienen comas.

attraction,visits_2025
Natural History Museum (South Kensington),7116929
The British Museum,6440120
Tate Modern,4514266
National Gallery,4147544
Tower of London,2817852
Detente y piensa

Pon la página al lado de esta lista. ¿Cuál de los números de la página no coincide con una fila? (El total es la suma de las cinco; una calculadora lo confirma, pero no hace falta.)

Respuesta

El de Tate Modern. La página dice 4,154,266; su fila dice 4514266: dos dígitos intercambiados. Nada te avisó, porque Quarto renderizó la oración fielmente: para Quarto son solo palabras. Para corregirlo, encuentra de dónde salió ese número.

La fuente del informe dice de dónde sale cada número. En la terminal:

cat report.qmd
---
title: "Five London Sights"
format: html
---

```{python}
#| echo: false
import csv

with open("data/visits.csv") as f:
    rows = list(csv.DictReader(f))

total = sum(int(r["visits_2025"]) for r in rows)
top = max(rows, key=lambda r: int(r["visits_2025"]))
free = [r for r in rows if r["admission"].startswith("Free")]
```

Five of London's best-known sights had `{python} f"{total:,}"` visits
between them in 2025. The most visited was the `{python} top["attraction"]`,
with `{python} f"{int(top['visits_2025']):,}"`, and `{python} len(free)` of
the five are free to enter.

Tate Modern, on the South Bank, had 4,154,266 visits.

Source: ALVA, "Visits made in 2025 to visitor attractions in membership with
ALVA" (only ALVA member attractions are counted).

Conociste estas partes en la Sección 1.2: la configuración entre las líneas ---, una celda de código que lee data/visits.csv y calcula total, top y free, y el código en línea, las piezas `{python} …`, que Quarto reemplaza por valores calculados. El Capítulo 7 explica cada línea. Por ahora, fíjate en qué se calcula y qué no. Todos los demás números de la página son código en línea que lee los datos; la oración de Tate Modern se escribió a mano.

NotaPor qué funciona

Un número escrito a mano es una copia, hecha una vez por una persona, y después nada la conecta con los datos. Los dígitos intercambiados son el desliz clásico al copiar, pero el problema de fondo es lo que pasa después: cuando cambian los datos, la copia se queda como estaba. Así es como un informe se desactualiza (Sección 1.1), y la Sección 5.5 te deja verlo ocurrir.

ImportantePruébalo

Revisa también el conteo de entradas gratuitas: cut -d, -f1,3 data/visits.csv muestra el admission de cada atracción.

Terminaste cuando contaste 4 filas que empiezan con “Free”, como dice la página, y puedes nombrar el único número que se escribió a mano en lugar de calcularse.

5.4 Empieza un historial

Antes de cambiar nada, registra el informe tal como está, para que siempre puedas volver a él. Git, que instalaste en el Capítulo 4, hace esto (Sección 1.4). En la terminal, en ~/first-report:

git init -b main
Initialized empty Git repository in /home/ana/first-report/.git/

La carpeta ahora es un repositorio: tiene una carpeta oculta .git donde Git guarda el historial. -b main le pone a la primera rama del repositorio, su línea de historial, el nombre main, como hace GitHub. (Esto necesita Git 2.28 o más reciente; git --version muestra el tuyo, y la preparación del Capítulo 4 instala uno más nuevo.) Pregúntale a Git qué ve:

git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
    .gitignore
    AGENTS.md
    README.md
    data/
    pyproject.toml
    report.qmd
    uv.lock

nothing added to commit but untracked files present (use "git add" to track)

Los archivos sin seguimiento (untracked) son los que Git puede ver pero todavía no registra. En la lista faltan tres cosas de la carpeta: .venv/, report.html y report_files/. Las deja fuera .gitignore, un archivo que enumera lo que Git debe ignorar; ls lo oculta porque su nombre empieza con un punto, y ls -a lo muestra. Nombra todo lo que uv y el renderizado reconstruyen, así que el historial guarda solo las fuentes.

Registra todo lo demás como el primer commit, un estado guardado con un mensaje que dice por qué:

git add .
git commit -m "Starter report, as copied"

git add . no imprime nada: elige qué entra en el próximo commit, y . significa “esta carpeta”, todo lo que no se ignora. git commit lo registra:

[main (root-commit) 15856fe] Starter report, as copied
 7 files changed, 916 insertions(+)
 create mode 100644 .gitignore
 …

Los siete caracteres después de root-commit nombran el commit; los tuyos van a ser otros. Revisa otra vez:

git status
git log --oneline
On branch main
nothing to commit, working tree clean
15856fe (HEAD -> main) Starter report, as copied

El árbol de trabajo (working tree) son los archivos de la carpeta tal como están ahora; “clean” (limpio) significa que están exactamente como los registró el último commit. git log --oneline enumera los commits, del más reciente al más viejo, y (HEAD -> main) marca el commit en el que están ahora tus archivos.

AdvertenciaError frecuente

Si git commit dice “Author identity unknown”, Git todavía no sabe tu nombre (el paso 5 del Capítulo 4 lo configura). Ejecuta las dos líneas git config --global que imprime, con tu propio nombre y tu correo, y luego vuelve a hacer commit. Si omites -m "…", Git abre un editor para el mensaje: sal sin guardar (en nano, Ctrl+X; en Vim, Esc, luego :q! y Enter) y vuelve a ejecutar el comando con -m.

ImportantePruébalo

Empieza el historial y haz el primer commit.

Terminaste cuando git log --oneline muestra un commit, y git status dice working tree clean.

5.5 Predice, cambia, reconstruye

Supón que ALVA corrige hacia arriba la cifra de Tate Modern en 1,000,000. Haz tú ese cambio en los datos, con nano, el pequeño editor de texto de la propia terminal. En la terminal, en ~/first-report:

nano data/visits.csv

Presiona la flecha hacia abajo tres veces para llegar a la fila de Tate Modern; su línea larga se sale por el borde derecho de la ventana, y no pasa nada. Presiona la flecha hacia la derecha hasta que el cursor quede justo después del primer dígito de 4514266, presiona Retroceso para borrar el 4 y escribe 5, para que el número diga 5514266. Guarda con Ctrl+O y luego Enter; sal con Ctrl+X.

AdvertenciaError frecuente

En nano, Ctrl+O (“write Out”, escribir) pide el nombre del archivo: presiona Enter para conservarlo. Ctrl+X sale; si no guardaste, nano pregunta primero: Y y luego Enter guarda, N descarta los cambios. Las teclas aparecen en la parte de abajo de la pantalla, donde ^ significa Ctrl. En una Mac, nano abre Pico, que usa las mismas teclas (comprobado en macOS 26, el 2026-11-12).

Antes de renderizar, pregúntale a Git qué cambiaste:

git status
git diff

Si el diff es más largo que la ventana, Git lo muestra de a una pantalla, con : o (END) en la última línea: presiona Espacio para ver más y q para recuperar el indicador. Las líneas eliminadas se ven en rojo y las agregadas, en verde.

On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
    modified:   data/visits.csv

no changes added to commit (use "git add" and/or "git commit -a")

Un diff son las líneas que un cambio eliminó y agregó. Las líneas reales son largas, así que aquí cada una se corta donde ves …:

diff --git a/data/visits.csv b/data/visits.csv
index eb394b9..8c1eea7 100644
--- a/data/visits.csv
+++ b/data/visits.csv
@@ -1,6 +1,6 @@
 attraction,visits_2025,admission,note,s…
 Natural History Museum (South Kensingto…
 The British Museum,6440120,Free (paid e…
-Tate Modern,4514266,Free (paid exhibiti…
+Tate Modern,5514266,Free (paid exhibiti…
 National Gallery,4147544,Free (paid exh…
 Tower of London,2817852,Paid,,"ALVA, Vi…

Léelo desde arriba. --- es el archivo antes, +++ después, y @@ … @@ dice qué líneas siguen. Una línea que empieza con - se eliminó, una que empieza con + se agregó, y una que empieza con un espacio es contexto sin cambios. Cambió una línea, en un archivo: exactamente la edición que querías.

Detente y piensa

Antes de renderizar: de los cuatro números del informe (el total, el conteo de la atracción más visitada, el conteo de entradas gratuitas y el de Tate Modern), ¿cuáles van a cambiar?

Respuesta

Solo el total, que sube en 1,000,000 hasta 26,036,711. El Natural History Museum (South Kensington) sigue siendo el más visitado, el conteo de entradas gratuitas sigue siendo 4 y la oración de Tate Modern sigue diciendo 4,154,266. Se escribió a mano, así que no puede seguir a los datos, ni siquiera cuando los datos cambian en la misma fila que describe.

Ahora reconstruye y mira. En la terminal:

uv run quarto render report.qmd

Vuelve a cargar report.html en el navegador (no se recarga solo). El total ahora dice 26,036,711, y la oración de Tate Modern no se movió. Esa es la desactualización de la Sección 1.1 en tu propia pantalla: cambió un dato de entrada, los números calculados lo siguieron y el escrito a mano se quedó atrás.

El valor de prueba no es real, así que deshazlo:

git restore data/visits.csv
git status
On branch main
nothing to commit, working tree clean

git restore devuelve un archivo a como estaba en el último commit. Es el deshacer de cualquier archivo que Git sigue, y es definitivo: el cambio que descarta nunca se registró, así que se pierde. Renderiza una vez más, y la página vuelve a 25,036,711.

ImportantePruébalo

Cambia los datos, predice, renderiza, compara, y luego restaura y vuelve a renderizar.

Terminaste cuando tu predicción coincidió con la página, y git status dice working tree clean.

5.6 Tres errores a propósito

Los errores son mensajes, no veredictos, y es más fácil aprender de ellos cuando los causaste a propósito. Para cada error de abajo, comételo, lee el mensaje y revisa una evidencia antes de corregir nada. Tres reglas para leer un error:

  • Busca la primera línea que diga ERROR o error, a menudo en rojo: dice qué salió mal. Cuando la sigue una traza de la pila larga, sube hasta ella.
  • Mira adónde apunta el acento circunflejo ^, cuando hay uno: ahí es donde el programa notó el problema.
  • Sáltate la traza de la pila. Muchos errores de Quarto terminan con Stack trace: y una lista de líneas que empiezan con at …, ocho para una carpeta equivocada y más de veinte para una configuración rota. Una traza de la pila (stack trace) enumera lo que se estaba ejecutando dentro de Quarto cuando se detuvo: es para los desarrolladores de Quarto, no para ti.

La carpeta equivocada

En la terminal:

cd ~
uv run quarto render report.qmd
ERROR: No valid input files passed to render

Stack trace:
    at _Command.actionHandler (file:///…/quarto.js:142967:11)
    …
Detente y piensa

Quarto no encontró ningún archivo para renderizar. Antes de cambiar nada, ¿qué revisas?

Respuesta

Dónde estás, y qué hay ahí: pwd imprime tu carpeta personal, y ls no muestra ningún report.qmd. El comando estaba bien y la carpeta estaba mal. Un nombre mal escrito, como reprot.qmd, da el mismo mensaje, y ls también lo muestra. Corrígelo con cd ~/first-report y vuelve a renderizar: la última línea es Output created: report.html.

Un error de tipeo en el comando

En la terminal, en ~/first-report:

uv run quatro render report.qmd
error: Failed to spawn: `quatro`
  Caused by: No such file or directory (os error 2)
Detente y piensa

¿Qué te dice la primera línea, y cuál es la solución?

Respuesta

uv no pudo iniciar un programa llamado quatro, porque no existe ninguno. El error repite el nombre: compáralo, letra por letra, con lo que querías escribir. Presiona la flecha hacia arriba para traer de vuelta el comando, corrígelo y presiona Enter. Sin uv run, la shell dice lo mismo con sus propias palabras: zsh: command not found: quatro en una Mac, quatro: command not found en Ubuntu.

Configuración rota

Abre report.qmd con nano report.qmd, borra el espacio después de los dos puntos en format: html para que diga format:html, guarda y sal. Luego, en la terminal:

uv run quarto render report.qmd
ERROR: YAMLException: can not read a block mapping
entry; a multiline key may not be an implicit key (4:1)

 1 |
 2 | title: "Five London Sights"
 3 | format:html
 4 |
-----^

Stack trace:
    at …

(La primera línea es una sola línea en tu pantalla, partida aquí para que quepa; la traza de la pila ocupa más de veinte líneas.)

Detente y piensa

El acento circunflejo apunta a la línea 4, que está vacía. ¿Dónde está el error, y cómo lo revisas?

Respuesta

En la línea 3, la de arriba. (4:1) significa línea 4, columna 1, contadas dentro del bloque de configuración, donde la línea 1 es el --- de apertura y se muestra vacía. Sin el espacio, format:html no es una opción de configuración, así que YAML, el formato de esa configuración, sigue leyendo y se rinde en la línea 4. Mira la línea del acento circunflejo y la de arriba. git diff muestra la única línea que cambiaste.

Corrígelo volviendo a poner el espacio, o con el deshacer general, git restore report.qmd. Luego vuelve a renderizar para confirmar: la última línea es Output created: report.html.

ImportantePruébalo

Comete los tres errores, lee cada mensaje, revisa la evidencia y luego corrígelo.

Terminaste cuando el renderizado termina con Output created: report.html, y git status dice working tree clean.

5.7 Pásale la corrección al agente

Sabes dónde está el número equivocado, puedes ver cualquier cambio con git diff y puedes deshacer uno con git restore. Ese es el momento de delegar: no antes de poder revisar el trabajo, sino en cuanto puedes hacerlo. Inicia tu agente en la carpeta del informe. En la terminal:

Tú haces 
cd ~/first-report
claude

Escribe codex o agy en lugar de claude si ese es tu agente. Confía en la carpeta cuando lo pregunte, porque la hiciste tú (en Claude Code, presiona primero la flecha hacia abajo: la opción empieza en No). (Codex pregunta aquí, y no en ~/setup, porque esta carpeta ahora es un repositorio de Git.) Luego, en el agente:

Pídele a tu agente 
En report.qmd, la oración sobre "Tate Modern" escribe a mano su conteo de visitas. Detente y piensa

El agente informa: “Listo. La oración ahora muestra la cifra de los datos”. ¿Por qué ejecutar git diff de todos modos?

Respuesta

El mensaje del agente es una afirmación sobre los archivos; el diff muestra los archivos mismos, cada archivo y cada línea que cambió, incluidos los que el agente no mencionó, como una edición de los datos.

El número escrito a mano desapareció, y en su lugar hay código en línea que busca Tate Modern en los datos.

Corrección. Vuelve a cargar report.html: la oración ahora debería decir 4,514,266, que es el 4514266 de la fila Tate Modern en la salida de cut de la Sección 5.3.

Si alguna de las dos revisiones falla, git restore report.qmd devuelve el archivo a como estaba antes de que el agente lo tocara, y puedes volver a pedirlo. Deshacer funciona con los cambios del agente exactamente igual que con los tuyos.

Cuando las dos pasan, haz commit, en la terminal:

git commit -am "Compute Tate Modern's visits from the data"
git log --oneline

-a agrega cada archivo seguido que cambió, así que no necesitas git add; -m da el mensaje. Tu hash, y quizá la cantidad de líneas, van a ser distintos:

[main d7e7f02] Compute Tate Modern's visits from the data

d7e7f02 (HEAD -> main) Compute Tate Modern's visits from the data

Reconstrucción. La última revisión pregunta si todo lo que necesita el informe está en el historial, y no solo en tu carpeta. Clona el repositorio en /tmp, una carpeta para archivos temporales que la computadora vacía de vez en cuando, y renderiza el clon. En la terminal:

git clone ~/first-report /tmp/first-report-check
cd /tmp/first-report-check
uv run quarto render report.qmd
Cloning into '/tmp/first-report-check'...
done.

El clon no tiene .venv/ ni report.html, porque .gitignore los dejó fuera del historial, así que el renderizado imprime otra vez Creating virtual environment y luego construye la página. (Si Git dice que el destino ya existe, ya hiciste esto antes: elige otro nombre, como /tmp/first-report-check2.) Abre la página del clon como abriste la tuya: open report.html (Mac), xdg-open report.html (Linux), o explorer.exe . y luego doble clic en report.html (Windows, en Ubuntu). Debería coincidir con la tuya, 4,514,266 incluido. Si el clon no se renderiza, algo que el informe necesita nunca se registró con commit: agrégalo y vuelve a hacer commit. Luego cd ~/first-report para volver; el clon es desechable.

ImportantePruébalo

Ejecuta el prompt, revisa su diff, haz commit y reconstruye desde un clon nuevo.

Terminaste cuando git log --oneline muestra dos commits, y la página del clon dice que Tate Modern tuvo 4,514,266 visitas.

Resumen

  • Un informe que se renderiza sin errores puede estar mal igual: pon cada número al lado de su fila en los datos, y rastrea uno equivocado hasta donde se escribió a mano.
  • Los números escritos a mano se desactualizan y los calculados siguen a los datos. Cambia un dato de entrada, predice, reconstruye y explica.
  • git status dice qué cambió, git diff muestra cómo, git restore lo deshace y git commit registra un estado al que puedes volver.
  • Lee un error desde su primera línea y el acento circunflejo, sáltate la traza de la pila y revisa una evidencia (pwd, ls, git diff) antes de corregir nada.
  • Delega un cambio en cuanto puedas revisarlo: alcance, corrección y reconstrucción (Tabla 5.2), y luego haz commit.
