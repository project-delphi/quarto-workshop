3  La vía rápida

Palabras clave

Quarto, publicación reproducible, agentes de programación, Markdown, Python, EPUB, análisis de datos, k-means

Ya usas una terminal y Git, y tienes un repositorio lleno de trabajo que termina, de una forma u otra, en documentos: un notebook, un script que escribe un archivo de resultados, un conjunto de pruebas. Este capítulo agrega Quarto a un repositorio así y lo lleva, en menos de una hora, a un informe en HTML, Word y PDF en el que cada número se calcula a partir de los resultados del propio repositorio, con una guarda que detiene la construcción cuando una oración deja de ser cierta, y revisado como pull request. Está escrito para quienes trabajan como analistas, en ciencia de datos o en ingeniería de ML o de investigación, y para quienes fundan una empresa con perfil técnico. Si la terminal o Git son nuevos para ti, toma la otra ruta, los capítulos 4 y 5 (Capítulo 4 y Capítulo 5), y vuelve a este capítulo después: da por sabido lo que ellos enseñan.

El repositorio es pequeño y realista: Acme Signals, una startup ficticia de dos personas, evalúa las versiones de un modelo que ordena los contactos de marketing de un banco según la probabilidad de que cada uno se suscriba, con datos públicos reales. La Parte III construye el resto de sus publicaciones a partir de los mismos resultados. Cada paso funciona igual en un repositorio propio, y la última sección dice qué cambiar.

En este capítulo
  • Agregar Quarto a un repositorio existente sin cambiar cómo se ejecuta su código.
  • Renderizar un notebook existente, y explicar qué le hace --execute.
  • Pedir un informe en tres formatos que calcule cada número a partir de los resultados del repositorio, y revisarlo como lo haría quien lo lee.
  • Proteger con una guarda una oración cuyas palabras dependen de los resultados, y revisar el cambio como pull request y desde un clon nuevo.

Partes deGit y una terminal en los que te mueves con soltura, un agente de programación (Capítulo 2) y el repositorio del taller clonado en ~/quarto-workshop.

Construyes~/acme-eval: el repositorio con AGENTS.md, un informe en HTML, Word y PDF, una guarda y una rama revisada como pull request.

3.1 ¿Es esta tu ruta?

Toma la vía rápida si todo esto es rutina para ti: moverte entre carpetas y leer un error en una terminal; git status, git diff, ramas y commits; instalar un programa de línea de comandos. Entonces necesitas cuatro herramientas, en las versiones de abajo, y un agente.

Si falta alguna, el agente la instala con el prompt de la Sección 4.5, y la Sección 4.4 instala el propio agente. Luego clona el repositorio del taller, que contiene el punto de partida, si todavía no lo hiciste:

git clone https://github.com/project-delphi/quarto-workshop.git ~/quarto-workshop

3.2 El repositorio

Copia el punto de partida y conviértelo en un repositorio propio, con un commit, como si lo hubieras clonado del repositorio de tu equipo. En la terminal:

Tú haces 
cp -R ~/quarto-workshop/starters/eval-repo ~/acme-eval
cd ~/acme-eval
git init -b main
git add .
git commit -m "Evaluation repo, as copied"

Es un proyecto de Python como muchos en la práctica, con diecinueve archivos y ni rastro de Quarto:

Ejecuta una vez sus propias comprobaciones, como lo harías con la rama de un colega, para conocer la línea base:

Tú haces 
uv run python scripts/evaluate.py
uv run pytest -q

El primer comando construye .venv/ a partir de uv.lock, ajusta las versiones y escribe outputs/; el segundo ejecuta las pruebas. Ninguno de los dos sabe nada de documentos, y nada en este capítulo cambia cómo se ejecutan. Ese es el diseño que hay que conservar: un script calcula los resultados una sola vez; todos los documentos los leen. Así los documentos se pueden reconstruir, cambiar de formato y revisar sin volver a ajustar nunca un modelo, y quien revisa puede confiar en que el informe y la ficha del modelo (model card) citan la misma ejecución.

3.3 Reglas antes que pedidos

Inicia el agente en el repositorio (claude, codex o agy) y dale las reglas del proyecto antes de cualquier trabajo. El prompt nombra lo que contiene un archivo de reglas, como el de la Sección 2.5, y le pide al agente que lea primero el código, para que las reglas se ajusten a este repositorio y no a uno genérico:

Pídele a tu agente 
Lee README.md, pyproject.toml, scripts/evaluate.py y tests/, y luego escribe AGENTS.md, en inglés, para este repositorio: su alcance (di que la empresa es ficticia); reglas (data/ es de solo lectura; los documentos leen outputs/ y nunca ajustan un modelo; cada número de un documento sale de outputs/ mediante código, nunca escrito a mano; ejecuta python, pytest y quarto con `uv run`; nunca hagas commit de outputs/ ni de los archivos renderizados); y los comandos para evaluar, probar y renderizar. Muéstrame el archivo.
Probablemente ejecute

lee las cuatro fuentes · escribe AGENTS.md

Lee lo que escribió. Cada regla debería ser una que puedas comprobar leyendo un diff: “los documentos nunca ajustan un modelo” se puede comprobar, “mantén el código limpio” no. Luego crea una rama para el trabajo, como harías con cualquier cambio que piensas revisar, y haz commit de las reglas en ella. En una segunda pestaña de la terminal:

Tú haces 
git switch -c add-report
git add AGENTS.md
git commit -m "Write the project's rules for agents"

3.4 Un notebook que ya tienes

La mayoría de los repositorios ya contienen notebooks. Quarto renderiza un archivo .ipynb directamente, a cualquiera de sus formatos de salida, así que un notebook se puede publicar antes de reescribir nada.

Pídele a tu agente 
Ejecuta `uv add ipykernel nbclient nbformat` y luego renderiza notebooks/explore.ipynb a HTML con `uv run quarto render notebooks/explore.ipynb --execute`. Dime dónde quedó el HTML y qué muestra `git status`.
Probablemente ejecute

uv add … · uv run quarto render notebooks/explore.ipynb --execute

Los tres paquetes son lo que Quarto necesita para ejecutar código de Python: un kernel y las bibliotecas que manejan un notebook. --execute importa. Un notebook se renderiza tal como se guardó: sin la opción, Quarto muestra las salidas guardadas en el archivo, o ninguna, y no ejecuta nada. Con ella, Quarto ejecuta primero cada celda y, como parte del vocabulario que hay que conocer, escribe las salidas nuevas de vuelta en el notebook.

Detente y piensa

Después del renderizado, git status muestra notebooks/explore.ipynb como modificado, además de pyproject.toml y uv.lock. No pediste que el notebook cambiara. ¿Qué pasó y qué haces?

Respuesta

--execute guardó en el notebook las salidas que calculó: en la prueba, varios cientos de líneas cambiadas. Conservarlas o no es una decisión del equipo, así que tómala a propósito. Este repositorio guarda sus notebooks sin salidas, así que deshaz ese cambio y haz commit solo de los dos archivos que registran los paquetes nuevos.

Tú haces 
git restore notebooks/explore.ipynb
git add pyproject.toml uv.lock
git commit -m "Add the packages Quarto needs to run Python"

El HTML quedó al lado del notebook, notebooks/explore.html, con una carpeta de archivos propios; .gitignore deja afuera los dos.

Un notebook también se puede convertir en un documento de Quarto: quarto convert notebooks/explore.ipynb escribe explore.qmd, texto plano que se compara y se revisa línea por línea, y que se ejecuta cada vez que se renderiza. Convierte un notebook cuando se está volviendo un documento que otros leen; déjalo como notebook mientras sea un lugar para explorar.

3.5 Un informe que lee los resultados

Ahora, el entregable: un informe de la evaluación para quienes deciden qué versión lanzar. Su métrica principal es el ROC AUC, la probabilidad de que una versión ponga a un contacto que se suscribió, elegido al azar, por encima de uno que no se suscribió, también elegido al azar: 0.5 es un orden al azar y 1, uno perfecto. Es un archivo .qmd nuevo al lado del código, y es la especificación, en un solo prompt, de todo lo que el informe tiene que hacer y de cómo lo vas a revisar:

Pídele a tu agente 
Ejecuta `uv run python scripts/evaluate.py`. Crea report.qmd, en inglés (formatos html, docx y typst; oculta el código), que lea solo outputs/: una oración que nombre la mejor versión según el ROC AUC, con su AUC y su intervalo del 95% como código en línea; una tabla con las métricas de cada versión, etiquetada `tbl-metrics`, con pie de tabla y citada en el texto; y las curvas ROC como una figura etiquetada `fig-roc`, con pie de figura y texto alternativo. Renderiza los tres formatos y dime qué AUC muestra cada uno.
Probablemente ejecute

uv run python scripts/evaluate.py · escribe report.qmd · uv run quarto render report.qmd → report.html, report.docx, report.pdf

Cada frase del prompt es vocabulario que corresponde a una función, y por eso puede ser corto:

Luego verifícalo de tres maneras (Sección 2.7). Lee el diff: git status debería mostrar report.qmd como nuevo y nada más cambiado, y el archivo debería leer archivos de outputs/ y no ajustar nada. Inspecciona el renderizado: abre report.html, report.docx y report.pdf. El renderizado imprime Output created solo para el primer formato, así que busca los tres archivos. En el proyecto terminado, que está en inglés como todo el ejemplo de Acme, la oración dice:

Of the three releases, v3 ranks best: its ROC AUC on the 11,303 held-out contacts is 0.799 (0.785 to 0.813).

Es decir: de las versiones, la que está en negrita es la mejor, con su ROC AUC sobre los contactos reservados para la prueba y su intervalo del 95%. Compáralo con la fuente, sin el informe: grep roc_auc outputs/metrics.csv imprime el valor de cada versión con su low y su high, y los tres formatos del informe tienen que coincidir con él.

AdvertenciaError frecuente

Word no recibe el texto alternativo. En las pruebas, Quarto 1.10.20 puso en la descripción de la imagen de Word el nombre del archivo de la figura, o nada, nunca el fig-alt; el HTML sí lo tenía. Si alguien que lee el archivo de Word usa un lector de pantalla, agrega la descripción en Word, y revisa cada formato que vaya a usar quien lee.

3.6 Una guarda para la oración

La primera oración del informe nombra a una ganadora. El código en línea mantiene sus números al día, pero la palabra “best” (la mejor), y el nombre que la acompaña, solo son ciertos mientras los datos lo digan. Una guarda es una línea de código al lado de una oración así que detiene el renderizado si la oración se vuelve falsa (Sección 23.4). Es Python común y corriente, así que encaja en el propio paquete del repositorio:

Pídele a tu agente 
Agrega src/acme_eval/claims.py con `claim(condition, sentence)`, que lanza un error que cita la oración cuando la condición es falsa. En report.qmd, protege con ella la oración que nombra la mejor versión, y agrega una regla a AGENTS.md, en inglés: una oración cuyas palabras dependen de los resultados lleva un `claim`. Demuestra que la guarda funciona: renderiza una vez con un nombre de versión equivocado a propósito, muéstrame el error, y luego restaura el correcto y renderiza de nuevo.

La demostración es lo importante. Una guarda que nunca viste fallar es una guarda que no probaste, y el prompt hace que el agente la rompa a propósito y te muestre el mensaje. Para que pueda fallar, la versión de la oración tiene que estar escrita en algún lugar donde una persona pueda equivocarse, y comprobarse contra outputs/: un nombre leído directamente de los resultados nunca podría contradecirlos. Cada agente redacta el mensaje a su manera; en el proyecto terminado dice:

ClaimError: The results no longer support this sentence: The best version named in this
report has the highest ROC AUC in metrics.csv.

Es decir, que los resultados ya no sostienen la oración: la mejor versión que nombra el informe tiene que tener el ROC AUC más alto de metrics.csv. Revisa después que el error deliberado ya no esté. Un renderizado fallido deja los report.html, .docx y .pdf anteriores donde estaban, así que un archivo viejo puede parecer un éxito: lee las últimas líneas del renderizado, y la oración en la fuente. Luego haz commit:

Tú haces 
git status
git add -A
git commit -m "Add a report that reads outputs/, with a guard"

.gitignore ya deja afuera outputs/, .venv/ y los archivos renderizados, así que git add -A toma solo fuentes: la regla nueva de AGENTS.md, report.qmd y claims.py. Igual lee antes git status: en la prueba, un notebook lleno de salidas entró en este commit porque se saltó la restauración de arriba, y git status fue donde se vio.

¿Dos minutos sin avanzar? Pega esto en tu agente. Respalda tu trabajo y lleva el proyecto hasta este punto; luego sigue leyendo desde aquí.

3.7 Revísalo como pull request

Un cambio que hizo un agente se revisa como el de un colega: en una rama, como pull request, con el diff leído archivo por archivo antes de que llegue a main (Sección 9.1). Sube el repositorio a GitHub, privado, y abre el pull request. En la terminal:

Tú haces 
git switch main
gh repo create acme-eval --private --source=. --push
git switch add-report
git push -u origin add-report
gh pr create --base main --fill

gh repo create … --source=. --push crea el repositorio a partir de esta carpeta y hace push de main; git push -u hace push de la rama; gh pr create --fill abre un pull request con el título y la descripción tomados de sus commits, e imprime su dirección. En la pestaña Files changed del pull request, o con gh pr diff en la terminal, revísalo como cualquier otro:

La última revisión es la que quien revisa no puede hacer leyendo. Clona el repositorio de nuevo y constrúyelo desde cero; primero van los resultados, porque outputs/ se calcula, no se guarda con commit:

Tú haces 
git clone ~/acme-eval /tmp/acme-check
cd /tmp/acme-check
git switch add-report
uv run python scripts/evaluate.py
uv run quarto render report.qmd

El report.html del clon tiene que mostrar el mismo 0.799. Un renderizado antes de la evaluación se detiene con FileNotFoundError para outputs/summary.json: es el clon diciéndote, con razón, que los resultados se calculan, no se guardan. Si falla cualquier otra cosa, algo que el informe necesita vive solo en tu carpeta: haz commit de eso y vuelve a clonar. Cuando el clon coincida, haz merge del pull request. Un servicio de construcción puede ejecutar la misma comprobación con un clon nuevo en cada pull request, para que nadie tenga que acordarse de hacerla.

3.8 En tu propio repositorio

Todo lo anterior se puede trasladar. Apunta los prompts a tus propios archivos:

  • Reglas. Nombra en AGENTS.md tu carpeta de resultados (outputs/, results/, reports/data/) y tus comandos. Si tu código calcula resultados dentro de notebooks, el primer trabajo es un script que los escriba en archivos: los documentos que vuelven a ejecutar un análisis son lentos y pueden contradecirse entre sí.
  • Dependencias. ipykernel, nbclient y nbformat se suman a tu entorno, mediante uv, Poetry, pip o conda, según como lo gestione tu proyecto; Quarto en sí es un programa aparte y no agrega ninguna dependencia de Python.
  • Deja afuera las salidas. Agrega a .gitignore los archivos renderizados y la carpeta de resultados.
  • Dónde vive el informe. En la raíz del repositorio, o en reports/; un solo archivo .qmd no necesita _quarto.yml. Una carpeta con varios documentos se convierte en un proyecto de Quarto (Sección 9.3).
ImportantePruébalo

Ejecuta los cuatro prompts y el pull request en el punto de partida, o en tu propio repositorio.

Terminaste cuando el pull request muestra las reglas, el informe y la guarda, sus tres formatos coinciden con outputs/metrics.csv y un clon nuevo renderiza el mismo informe.

Resumen

  • Quarto se suma a un repositorio existente como un archivo .qmd y tres paquetes de Python; cómo se ejecuta el código no cambia.
  • Calcula los resultados una sola vez, en un script, y escríbelos en archivos; cada documento lee los archivos y no ajusta nada.
  • Un notebook se renderiza tal como se guardó; --execute lo ejecuta y escribe las salidas de vuelta en él.
  • Un prompt hecho de funciones con nombre (“código en línea”, “etiquetada tbl-metrics”, “texto alternativo”) obtiene esas funciones, y cada una trae su revisión.
  • Protege con una guarda las oraciones cuyas palabras dependen de los resultados, y mira fallar cada guarda una vez.
  • Revisa el cambio como pull request, y reconstrúyelo desde un clon nuevo.

El informe es la primera de las publicaciones del proyecto. La Parte III construye el resto a partir de los mismos resultados: una ficha del modelo, una presentación para las partes interesadas, un sitio del proyecto con una sola marca y un documento técnico (white paper). Si llegaste por la vía rápida, la guía de Londres de la Parte II queda ahí como referencia para cuando un capítulo la mencione.
