14  Reports That Run Themselves

Keywords

Quarto, reproducible publishing, coding agents, Markdown, Python, EPUB, data analysis, k-means clustering

Much of what an organisation publishes is the same document with different numbers: the monthly update for investors, one report per customer, region or team. Built by hand, each copy starts as last month’s file, and each is a chance to leave one of last month’s figures in it. Built from one source with a parameter, a value given when the document is rendered, each copy is the same tested document run on a different value, and a script can make every one of them and check it.

An illustration

A founder writes this month’s update the usual way: open last month’s, save it under a new name, change the figures. Revenue, changed. Customers, changed. The sentence in the third paragraph that says the month was the best so far is not a figure, so it is not changed. It goes to every investor. Nobody lied, and nothing in the file was able to object.

This chapter makes Acme’s monthly update and a report per customer segment. The update’s business figures are synthetic, and say so on every number; the model’s figures beside them are the real evaluation’s.

In this chapter
  • Explain what a parameter is, where its default lives, and how a value is passed at render time.
  • Ask for a parameterised document that validates its value and chooses its value-dependent words by code, with guards.
  • Render one document for every value with a script that names and checks each output.
  • Say where the outputs of a parameterised document land in a website project, and why.

You buildupdate.qmd, segment.qmd and a script that renders every month and segment; a feedback sheet for every section.

What you will build

14.1 One document, many values

A parameter is a value a document is given when it is rendered. Its default lives in the document, in a cell tagged parameters: the finished update’s month defaults to “latest”, which it reads as the last month in its data, so its default never goes stale. The segment report defaults to age_band 60+, and the feedback sheet to section A.

quarto render update.qmd -P month:2026-06 replaces the default for one render: Quarto adds a cell after the parameters cell that sets the new value, and the document runs as before. That cell is executed through papermill, a Python package the project must have: without it, a render with -P stops with The papermill package is required for processing --execute-params.

Two rules make a parameterised document safe:

Validate the value
A month or a segment that is not in the data stops the render with a message listing the valid ones, rather than producing a report about nothing.
Let code choose the words
“Up” or “down”, “above” or “below”, “the first month, so no change”: chosen by code from the numbers as printed, a word cannot disagree with them. Guard what code cannot choose, such as a typed caption.

A guard that repeats the comparison that chose the word can never fail, and protects nothing. The finished update’s guard checks the printed figures instead. A document rendered for ten months is as many chances for a typed word to be wrong.

14.2 The investor update

The update comes in two turns: first the document and its parameter, then the sentence that compares one month with the month before, whose wording code must choose.

Ask your coding agent 
Run `uv add papermill`, then create update.qmd, a monthly investor update parameterised by `month` (a cell tagged `parameters` whose default is "latest", meaning the last month in data/synthetic_business.csv): that month's business figures, each labelled synthetic, and the release live that month with its real model metrics from outputs/. Stop with a clear message if the month is not in the data. Formats html, docx and typst; render it with `-P month:2026-06` and tell me where the files went.
Expect it to run

uv add papermill · writes update.qmd · uv run quarto render update.qmd -P month:2026-06

Ask your coding agent 
In update.qmd, add the change from the month before, its wording chosen by code from the printed numbers and guarded; the first month says there is no earlier one. Render 2026-06 and the first month in the data, and show me both sentences.
Expect it to run

edits update.qmd · renders it twice, with -P month:…

Check it as an investor would, and as an auditor would. Every business figure says it is synthetic, here; in your own update, every figure names its source. The model’s figures come from outputs/ and are the real evaluation’s. A month before the first release says so, rather than inventing a model figure. And a month that is not in the data stops the render: try -P month:2027-01.

Pause and think

The finished update was rendered for its last two months, 2026-09 and 2026-10, from one source. Between the two, which sentences should differ: the figures, the change from the month before, the release that was live? Which must not?

Answer

Six differ only in their figures and months. One changes its words: “Pilots: 4 (synthetic), unchanged from August 2026” becomes “Pilots: 2 (synthetic), down from 4 (synthetic) in September 2026”. Two appear only in 2026-09, when its release was new. Nine are word for word the same, the synthetic label and the method note among them: if those differed, a parameter would have leaked into text it should not reach.

Here is the mechanism, in the finished update. You need not read every line: in its parameters cell, with its comments cut to fit a phone, the last line is what matters, the parameter and its default.

#| tags: [parameters]
# "YYYY-MM", or "latest": the last
# month in data/synthetic_business.csv
month = "latest"

And the lines of its change() that choose the word for one figure, from the two figures as printed, and guard the choice:

printed_now, printed_before = show(now[column]), show(before[column])
word = params.direction(*(float(re.sub(r"[^0-9.-]", "", p)) for p in (printed_now, printed_before)))
claim((word == "unchanged") == (printed_now == printed_before),
      f"{FIGURES[column][0]}: the printed figures agree with '{word}'.")
if word == "unchanged":
    return f"{text}, unchanged from {previous_label}"
return f"{text}, {word} from {show(before[column])} {SYNTHETIC} in {previous_label}"

params.direction() reads the numbers back from the two printed figures and returns “up”, “down” or “unchanged”, so the word follows the figures as printed, not the unrounded data. The guard checks one thing, by a different route: the word is “unchanged” exactly when the two printed figures are the same text. So it catches a parse that goes wrong; telling “up” from “down” is direction()’s job, which a unit test pins. For 2026-10, the update wrote “Paying customers (banks): 8 (synthetic), up from 6 (synthetic) in September 2026”.

WarningCommon pitfall

The update is not in the site’s render list, and should not be: it is not a public page. So Quarto renders it beside its source, not in _site/, and the batch script moves each file into reports/.

14.3 One report per segment

The same pattern makes the per-customer, per-region or per-team report: one document, one parameter per dimension.

Ask your coding agent 
Create segment.qmd: a one-page report for one customer segment, parameterised by `factor` (age_band or job) and `segment` (default 60+), with the best release's metrics for that segment from outputs/segments.csv against the whole list, wording guarded, and a note when the segment has few subscribers. Render it with `-P factor:job -P segment:student`.

A segment’s numbers deserve more caution than the whole list’s: a segment with few subscribers has wide, noisy rates. The finished report adds its note below 50 subscribers, a named setting, FEW_SUBSCRIBERS, in the project’s code; the right threshold is your call, and belongs in a setting like that, not in a sentence.

14.4 Every value, checked

Ask your coding agent 
Write scripts/render_params.py: render update.qmd for every month in data/synthetic_business.csv and segment.qmd for every age band, in html, docx and typst, each file named by its value, into reports/; check that every file exists and contains its value; print a table.

For the finished project that is ten months and five age bands in three formats: 45 files, each named by its value and each checked for it. The check is what makes a batch trustworthy: one file that silently shows the default month, because a value was not passed, would otherwise go out with the rest.

Stuck for two minutes? Paste this into your agent. It backs up your work and brings the project to this point; then carry on from here.

Catch me up: follow ../quarto-workshop/checkpoints/19-eval-params/README.md
ImportantTry it

Make the update, the segment report and the batch script.

You’re done when render_params.py reports every file present and showing its value, a month outside the data stops the update with a list of valid months, and every business figure in the update says where it comes from.

14.5 For teachers: a sheet per section (optional)

The same method serves a teacher with several sections of one course: one feedback sheet per section, from one gradebook. The example’s gradebook is synthetic, three sections of students identified only by number.

Ask your coding agent 
Create feedback.qmd: one feedback sheet per section of data/gradebook.csv, parameterised by `section`, with that section's mean and spread for each assignment against the course, a chart with alt text, every sentence labelled synthetic and its wording guarded, and no student identifiers. Then write scripts/render_sections.py to render feedback-<section>.pdf for every section and check each one. Run it.

Marks are personal data, so the sheet shows section totals only, and stops if any group it describes has fewer than 5. With real marks, Section 2.10 and your institution’s data policy come first: build on a synthetic gradebook with the same columns, and render the real one yourself.

Summary

  • A parameter is a value given at render time; its default lives in a cell tagged parameters, and -P name:value replaces it, through papermill.
  • Validate every value, let code choose every word that depends on it from the numbers as printed, and guard what code cannot choose.
  • Name every output by its value, and render and check them all with one script.
  • A parameterised document left out of a site’s render list renders beside its source; move its outputs where they belong.
  • Label synthetic figures on every number, and keep personal data to group totals.
